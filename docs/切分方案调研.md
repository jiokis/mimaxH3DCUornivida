# MiniMax-H3 视频切分方案调研（长视频分段二采）

## 背景与问题
H3 单段生成帧数受限：960p 下 ~124 帧安全（192s/it），192 帧飙到 1504s/it（慢 8 倍），
345 帧直接 OOM（需 70GiB > 64GiB）。因此 15s 长片必须**切段分别二采再拼接**。

### 我们的切分痛点（实测）
1. **丢帧过多**：旧 `grid_floor`（向下取整 17n+5）每段丢 5-16 帧，5-7 段累计丢 2-3 秒
   → 15s 请求产出 12s 成片
2. **大段悬崖**：切点恰好落在 138 帧 → 二采 812s/it 慢 8 倍，客户端 timeout 挂起
3. **碎段**：密切点时产生 22 帧(0.9s)碎段，节奏破碎
4. **客户端健壮性**：twopass 客户端被 timeout 杀后，ComfyUI 服务端继续完成但无人接收

### 我们的当前方案（已修复）
```
grid_nearest（就近网格 17n+5）+ 最小段保护(<39并入) + 大段缩124 + 余量传递
→ Σ段帧数 ≈ base 帧数（误差 ≤3 帧），15s 保留
→ 最大段 ≤124，避开悬崖
+ 段完整性校验（缺段不产出残片）
+ h3_gen_wire 落盘确认（SaveVideo 写完才 DONE）
```

## 社区成熟方案调研

### 方案 1：官方/社区「逐段独立生成 + 拼接」（我们当前的路线）
- 代表：`ComfyUI_MiniMaxH3_Director`（★1696，AIMixer）
- 思路：多段 Director 分别生成，各自完整音轨，硬切拼接
- 优点：实现简单、每段独立可控
- 缺点：段间无 latent 连续性；音频有 AAC 帧填充漂移（我们已用音床合流解决）

### 方案 2：首帧续接（FL2VA / i2v）
- 代表：官方 FL2VA、`ComfyUI-H3-Motion-Context`（★960）
- 思路：上一段末帧作下一段首帧，保持运动方向与速度
- 优点：段间动作连续
- 缺点：**尾帧会锁死视觉状态**（含光照/场景/姿态）；有意的状态改变会被上一段压住
- 适用：同场景连续动作（幕内接续），不适用快切/场景切换

### 方案 3：Audio Lock（T8 节点）
- 代表：`comfyui-minimax-h3-audio-T8`（★1051）、joeygambino Multishot 的 audio_lock
- 思路：`audio_mode="lock_source"` + `audio_denoise_strength=0`，音频 latent 锁进源音频不进采样器
- 优点：音频相关 0.9985-0.9995
- 缺点：需要 T8 节点（GitHub 下载受阻）；且文档明确指出**最终音轨不要靠拼接对齐**，
  应直接用音床整体合流（相关度 0.9999，逐样本一致）

### 方案 4：Native Continuation / latent 续接（LongMedia）
- 代表：`ComfyUI-MiniMax-H3-LongMedia`（vizart-vj）
- 思路：消费上一段的服务端 latent，逐帧钉住结尾、音频从接缝继续
- 优点：接缝画面差 2.6-7.0 vs 无续接 32-68（官方实测）
- 缺点：同场景专用；跨档位/分辨率会显式报错；跨场景不要续接

### 方案 5：Latent Split（bbaudio-2025）
- 代表：`Comfyui-MiniMax-H3-LatentSplit`
- 思路：latent 分割做长视频
- 说明：长视频 latent 分割，未实测，需评估

## 结论与推荐

### 快切蒙太奇（我们 90% 的题材）
**当前方案已是最优**：逐段独立生成 + 音床合流 + tpad 补帧。
快切本来就该硬切，不需要 latent 连续性；音床合流解决音频漂移。

### 连续动作长片（未来可能）
用 **方案 4（continuity_from 链式续接）**：消费上一镜 latent，逐帧钉住结尾。
硬约束：① 首次续接的上一镜必须也是链式实现渲染；② 链内分辨率/档位一致；③ 跨场景不续接。

### 待验证的改进点
1. **场景检测阈值自适应**：暗场景（灯塔/夜街）检不出切点 → 需更低阈值或光流
2. **切点吸附到镜头边界**：目前切点是模型自发的，与提示词 [Shot N] 设计有偏差
3. **T8 lock_source 落地**：等 GitHub 可访问后装 T8，替代手工音床合流（更省心）
4. **LongMedia 评估**：连续动作场景实测
